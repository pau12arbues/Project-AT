Objectives  • Build a distributed application interacting with multiple real services and interfaces (Bicing1, Telegram2, AWS3, IP API4, Air Pollution Quality Index5, Open Gateway 6). • Communicate asynchronous processes. • Work and learn real interfaces based on REST and JSON. • Deploy services in the cloud (AWS). • Build a small HTML page to make GET/POST requests using AJAX. Description  The aim of this project is to implement a system that notifies users with two types of Telegram messages to user phones: one with the free slots of the Bicing stations the user has previously subscribed to and other with the air quality index (AQI) of the user location based on the IP. For this purpose, some external services will be used: Bicing, Telegram, AWS, IP API, Air Pollution Quality Index and Open Gateway.  The functionality of the application is as follows:  The main service is the Bicing Free Slots/Air Quality Notifier (BAN). The requirements of this service are:  • Access and save bicycles information from Bicing API. This API must be accessed the first time a request is received and it must save the stations and their status during some configured time (cache). After expiring this time, the first request related to bicycles must recover the information from Bicing API again and save it to cache. • Allow users to subscribe to a list of Bicing stations using their phone number. This service is restricted to users aged 18 or older, so it must use the Verify Age API from Open Gateway to validate the user’s age before registering them in the system. If the provided phone_number belongs to a user who does not meet the age requirement, an error must be returned, and the user must not be registered.  • Send a Telegram message to the users with the free slots of the stations they have previously subscribed to. • Send a Telegram message to the users with the Air Quality Index of the city where the IP the device making the request is connected. • This service must be deployed in an AWS EC2 instance in the same way it was made in the last seminar.  To accomplish these requirements, the BAN must publish a REST API with three services producing and consuming messages in JSON format:  • Stations service, with one method:  o Get stations: Returns the stations list with the same information retrieved from the Bicing API. A request to this method must return the cached information and not make a request to the Bicing service. If cache is empty, it must recover the information from Bicing API directly. What you do over HTTP is send messages from your bot to a chat using the Telegram Bot API. • In private chats, like the one we created, it is NOT possible to obtain the chat_id if the user has never sent a message to the bot. Telegram protects privacy in this way: o A bot cannot “discover” users. o The first message is always initiated by the user. o A bot only knows a user after that user sends a message. • If you add the bot to a group chat, the bot receives the my_chat_member event, and then it is possible to access the chat_id of the group. Even without anyone sending a normal message, the “added” event already contains the chat_id. • The chat_id identifies the chat, not the bot. And in private chats, chat_id == user_id, so if you create multiple bots, each will have a different token, but the chat_id will be the same. o If you send messages to two different chats created with bots from the same account, the chat_id will be the same because the chat is still the same (your user). o The token identifies the bot, and it is what Telegram uses to know who is sending the message. o Each bot has its own unique token. o Even if the chat_id is the same, Telegram knows which bot is sending the message thanks to the token you use. o An analogy would be: the bot is a phone, and the chat_id is your phone number. You call two different phones, but your number remains the same.  Accessing Open Gateway APIs  Open Gateway is an initiative spearheaded by the GSMA in collaboration with leading telecommunications operators, cloud providers, and aggregators worldwide. GSMA Open Gateway currently offers a variety of APIs, including those for Identity and Fraud Prevention, Location Services, and Communication Services: https://opengateway.telefonica.com/. 
In our project, we will use only one of these APIs, Verify Age Threshold, to validate that the age of the subscriber associated with a phone number is equal to or greater than a specified age threshold: https://developers.opengateway.telefonica.com/reference/verifyage One of the objectives of this project is to gain hands-on experience with real-world API development. For this purpose, it is necessary to: 1. Read the Open Gateway documentation. 2. Sign up for an account and obtain the necessary API credentials to access the services in the Sandbox. Your application must have access to the Age Verification API. In the usage mode, select mock mode. At the end of the setup process, you will have created an application with a client ID and client secret, which are required to obtain a token from the AuthServer to access the API. As standardized by CAMARA, access to Open Gateway APIs is secured using OpenID Connect (OIDC) on top of the OAuth 2.0 protocol. We will use the backend authorization flow, as we want to access Open Gateway APIs from our backend without end-user interaction, following the OIDC CIBA (Client-Initiated Backchannel Authentication) flow. For this project, the API must be integrated via HTTP requests directly, i.e., without using an SDK.
